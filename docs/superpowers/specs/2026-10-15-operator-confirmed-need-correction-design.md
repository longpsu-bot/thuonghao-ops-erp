## 1. Accepted meaning and technical decision requested

D-044 and operator brief C already authorize an append-only correction after PO/PXK commitment. Positive affected supplier/date commitments use complete replacement POs; authoritative zero retains CANCELLATION_REQUIRED and blocks PXK; corrected PXK needs explicit successor release. No supplemental/cancellation execution policy is proposed. Ordinary work can use one authorized Actor; existing capabilities, scopes and exception owners remain.

Approve or revise this technical architecture: a dedicated quantity-correction preview and atomic reopen-plus-Save command, with one strict private continuity classification reused by canonical Allocation/PO/PXK consumers. Preserve unchanged allocation revisions and split identities rather than regenerating them and later hiding resulting staleness.

The key invariant is exact unchanged immutable Need revision/decision membership plus complete Supplier facts. Equal totals, names, current pointers alone or a later numerical reversion never establish continuity.

## 3. Proposed API boundary

Names and new contract discriminator below are proposals, not installed APIs.

`get_confirmed_need_correction_preview(request jsonb)` — read-only `CONFIRMED-NEED-CORRECTION.v1` envelope:

```text
payload: {
  need_generation_run_id, expected_need_generation_run_version,
  confirmed_need_batch_id, expected_confirmed_need_batch_version,
  confirmed_need_line_id, expected_current_revision_id,
  expected_current_decision_id, proposed_confirmed_quantity,
  reason_code, reason_note
}
```

Returns canonical before/after/delta and exact quantity errors; full affected family contribution/School scope; retained Supplier splits/notes; authorized whole-PO documents and current/future attention; applicable actions and disabled reasons; a server proposal fingerprint bound to source identities, versions and reviewed quantity. Changed allocation proposals are explanatory and not accepted allocations. Visible PO coverage is always AUTHORIZED_DOCUMENTS_ONLY; absence never means no commitment. Missing Procurement visibility must not add a correction-write capability prerequisite.

`correct_confirmed_need(request jsonb)` — normal closed command envelope with command/correlation/idempotency, expected batch version, actor, requested time, governed reason/note; proposed outer reason CONFIRMED_NEED_CORRECTION_SAVED; payload repeats exact preview inputs plus proposal fingerprint. Outer/payload batch versions must agree or fail validation. One selected School/date/Ingredient stable line initially; unrelated lines are omitted from Save. Ordinary unreleased Save remains unchanged. Legacy overlap/range/source-stale guards are not silently bypassed or used to regenerate a run.

The correction preview must reuse shared canonical quantity/policy validation through a private trusted correction context, separating only its lifecycle precondition. Do not suppress arbitrary blockers, execute a write-and-rollback preview, duplicate all quantity rules or add a browser-controlled validation bypass.

## 4. Atomic command, locks and security

1. Validate the closed envelope and resolve JWT-bound Actor; require existing prepare/reopen and Save capabilities/scopes. Existing prepare requires planning.need_generation.write and, when reopening released authority, confirmed_need_release.release; Save requires confirmed_need_quantities.confirm with its existing GLOBAL boundary. One Actor may hold them all; none are automatically granted.
2. After those envelope/JWT/capability/scope checks, look up the outer idempotency receipt and return the stored outcome for an exact replay before resolving mutable currentness or generating child commands. A successful exact request must replay after its own successor or a later source correction. Only NEW requests resolve the current run/batch/line and proposal, acquire the ordered locks below and reject stale or unsupported chains. Derive separate prepare/Save child identities and idempotency keys from the outer receipt plus closed stage names; never reuse the outer ID.
3. Reuse correction advisory/run/batch lock order, then authoritative selected line/revision and Unit/policy binding checks. Serialize against release/Save through the existing batch lock. Revalidate after waits; do not validate from the browser's projected universe. No informational PO/PXK locks are added.
4. Inside one rollback subtransaction, invoke existing prepare with a distinct deterministic child identity, then Save with the returned reopened version and exact selected line. Record before/successor revision/decision IDs and affected source identities in the existing event/audit/receipt evidence. No new derived-state table is proposed.
5. Any child failure rolls back reopen, Handoff invalidation, Save, child receipts and events together. Retryable failures do not retain a misleading outer success; nonretryable failed outer receipt may remain under the reviewed receipt convention. Return complete authoritative readback and explicit no-commit certainty when proven.

Local read-only catalog evidence: prepare is owned by atlas_need_generation_runtime; Save/reopen by atlas_confirmed_need_review_runtime. Both public commands are SECURITY DEFINER with empty search_path and authenticated entry only. This is a catalog privilege addition, not additional human authority: authenticated already has that command entry, and the child still checks the same Need/release capabilities and GLOBAL. The new wrapper must ALSO independently retain the Save capability requirement. Existing child Actor checks remain identical. The two proposed bounded public APIs necessarily require authenticated EXECUTE, with their existing-style JWT Actor/capability/scope checks. Those two exact public signatures are the only proposed new browser entry grants; PUBLIC, anon and service_role receive no EXECUTE. No additional browser access to private helpers/tables, runtime role membership, new capability or GLOBAL assignment follows. Private helper grants remain exact runtime-only EXECUTE. These proposed catalog additions require explicit architectural review; they are not installed or accepted by this packet.

Preview retains the existing Confirmed Need read capability/GLOBAL gate; PO details additionally respect the existing Procurement read capability and whole-PO scope. Its command authority is unaffected by disclosure. The preview may need a private read-runtime-owned authorized-PO projection exposed by EXECUTE only to its command/read owner. ## 5. Strict continuity and pending-versus-zero algorithm

Build the complete canonical current source universe, including zeros and overlapping/ambiguous batches. A family classification is derived evidence, not a persisted lifecycle/status. Separate two uses of the same immutable comparison:

- **Prospective Preparation eligibility:** unchanged accepted Supplier facts may cover exact current CN facts before Planning re-release/new Handoff. Readiness is evaluated before those child releases; requiring a successor here would deadlock the workflow.
- **Official PO/PXK applicability:** require current released Need, its complete current approval/release evidence, and a successfully explicitly released current successor Handoff, in addition to exact adjacent-edge comparison. Prospective eligibility alone never makes an official document current.

Distinguish exact current, prospective unchanged, officially proven continuity, pending correction, genuine authoritative zero and unavailable/ambiguous source. An additive derived pending reason/read classification is an API proposal for review, not a new durable lifecycle.

For a retained current PURCHASE_HANDOFF allocation family, prove all of the following:

- Same stable family/date/location/Ingredient/Unit identity and every-and-only contribution membership. Resolve the original confirmed decision through Handoff line → purchase_demand_references.confirmed_need_snapshot_line_id → approval snapshot.confirmed_need_validation_attempt_id → immutable confirmed_need_validation_lines.current_confirmed_need_line_decision_id (RMVP-07 migration 20260805202517, lines 1490–1510), not merely the stable line's current pointer. Missing legacy evidence fails closed.
- Each original confirmed Need revision and decision remains the exact current authorized immutable pair, with identical School, customer lineage, destination, quantity, Unit and source facts. A regenerated Need revision, D-040 carry, policy-incompatible fact, removal, additional contributor or ambiguous universe is not this proof.
- Across every adjacent Handoff predecessor edge, require the same stable Handoff line and exact confirmed revision/decision and approved quantity/Unit facts, with no missing/extra contribution. Never jump over a changed edge, compare only chain endpoints or resurrect authority after a changed-and-reverted interval. Reject gaps/cycles; any traversal bound fails closed.
- Preserve the entire accepted Supplier split set, quantities, ratios, origins and notes; apply existing effective Supplier/eligibility checks at their established boundary. Current Master Data display rename does not rewrite frozen output evidence.

When the prospective immutable comparison succeeds, strict allocation readiness and preparation readiness can accept the unchanged accepted allocation before re-release; changed families still need an explicit accepted allocation. After Planning and successor Handoff release succeed, the official comparison validates that released successor chain and promotion skips creating a new family revision, contribution or split. A header/line-ID renewal with unchanged immutable Need facts must not force a child allocation Save.

Raw Handoff fingerprints remain different and immutable. Keep school_catering_family_projection and every writer's expected-source binding raw; never globally return the old fingerprint to satisfy writes. A separate derived applicability predicate makes the exact retained allocation usable by the appropriate consumer. Current reads may disclose proof/currentness separately without substituting an obsolete source fingerprint into command requests. Keep existing fingerprint algorithms and historical foreign keys.

Preserving contribution IDs also preserves canonical interval ordering and School-to-Supplier overlap. Regenerating random contribution IDs and comparing only a set/total could silently redistribute School coverage even when quantities match.

During the reopened interval, no active Handoff alone means **pending**, never zero. Use current complete CN facts and the successful correction's exact existing command/audit evidence to identify that interval. Unchanged facts can be prospectively eligible for Preparation; official PO/PXK currentness remains pending until current released Need and successor Handoff exist. Old released documents remain externally active and immutable, but are not falsely certified current or needlessly regenerated. Changed facts require explicit allocation/release. Genuine zero requires complete authoritative source evidence; incomplete/ambiguous/missing source cannot create cancellation-required. A zero proposal must be shown as such without inferring an executable supplier cancellation.

After explicit successor Handoff release, the same proof traverses its direct predecessor links. For changed families, retain existing explicit allocation Save, promotion and complete document replacement behavior. Same Supplier numerical total with changed Need/School lineage is still affected. No definition based on commercial totals alone is proposed.
