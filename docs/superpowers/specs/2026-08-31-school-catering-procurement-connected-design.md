# School-Catering Procurement Connected Design

**Status:** Written design for user review  
**Date:** 2026-08-31  
**Architecture authority:** OPS_SYSTEM_MAP v1.0 / ARCH-002  
**Repository baseline:** `main` at `9928ced99e9d0430801140ad29f86b716d594e59`  
**Scope:** Connected school-catering Planning → Procurement flow, Allocation Families, supplier splits/rebalancing, PO drafts, PO release, and connected operator UI.  
**Out of scope:** released-PO amendment/cancellation/replacement, supplier acknowledgement, Warehouse/Dispatch/Finance execution, Retool mutation, Live OPS mutation, and Admin numbering remediation.

## 1. Executive decision

The connected school-catering Procurement flow is:

```text
PLANNING
Confirmed Need
  → Chuyển sang lên đơn
  → Confirmed Need released for Purchase Handoff
  → school-catering Purchase Handoff materialized + released

PROCUREMENT
Phân bổ nhà cung ứng
  → Allocation Families
  → priority-1 supplier proposed at 100%
  → operator confirms / changes / splits
  → exact balanced supplier allocation
  → Tạo đơn mua

Đơn mua
  → DRAFT PO per supplier + service date
  → Phát hành cho NCC
  → official PO number generated by backend
  → RELEASED_TO_SUPPLIER
  → PDF / export
```

Purchase Handoff remains a durable Planning-owned backend boundary but is not a separate operator screen. Procurement begins with the first real purchasing decision: supplier allocation.

The Allocation Family is the Procurement decision aggregate because it preserves OPS v1's useful split/rebalance behavior while Atlas retains exact Purchase Handoff lineage underneath it.

## 2. Contract precedence and non-conflict

### 2.1 PA-05E wholesale remains unchanged

This design does **not** replace PA-05E or the existing supplier-direct wholesale contract:

```text
Released Dispatch Requirement
→ exact one-supplier-per-line fulfilment allocation
→ released Supplier Purchase Order
```

Existing PA-05E commands, tables, tests, privileges, and one-supplier-per-requirement-line behavior must remain compatible.

### 2.2 This document governs school catering

School catering has proven operating requirements that differ from PA-05E:

- many schools/delivery locations;
- multiple suppliers may split one ingredient demand family;
- supplier decisions are made against an aggregate family total;
- saved split ratios support rebalance after upstream quantity changes;
- one supplier/date PO may contain lines for multiple schools.

The current `pa-06a-operator-workflow-matrix.md` CMD-05/CMD-06 supplier-direct flow must therefore not be interpreted as a school-catering one-supplier-per-line requirement.

### 2.3 Dormant prototype is not authority

`src/modules/procurement/ProcurementWorkbench.tsx` is a fixture-driven prototype with a broader seven-step lifecycle. It may supply implementation clues only. The connected UI must be built from this contract and authoritative Atlas reads/commands.

## 3. OPS v1 evidence to preserve

Retool remains workflow evidence only.

Preserve these operational behaviors:

- date-range and multi-school scope;
- dense master/detail work surfaces;
- search and exception filters;
- family grain equivalent to date + school + ingredient;
- family-atomic supplier allocation saves;
- multiple supplier split rows;
- positive `split_qty`;
- exact `Σ split_qty = family total` validation;
- persisted split ratios;
- deterministic ratio-preserving rebalance with final residual closure;
- PO grouping by supplier + service date;
- school/ingredient detail on PO lines;
- supplier-oriented PDF/XLSX output.

Do **not** copy:

- direct SQL from UI;
- Retool's coupling of Procurement, Warehouse and Dispatch;
- silent rebuild of already released PO lines;
- fixture/local state as authority;
- operator-entered system codes or official document numbers.

## 4. Planning → Procurement boundary

The current school-catering command `release_confirmed_needs_for_purchase_handoff` moves Confirmed Need to `RELEASED_FOR_PURCHASE_HANDOFF` but does not materialize a school-catering Purchase Handoff.

The visible `Chuyển sang lên đơn` action therefore performs two durable commands in sequence:

1. existing Confirmed Need release;
2. `release_school_catering_purchase_handoff`.

If step 1 succeeds and step 2 fails, Atlas shows the valid intermediate state and a retry action. It must not pretend both operations rolled back.

After Purchase Handoff release, Procurement consumes immutable Planning facts: ingredient, quantity, controlled unit, service date, delivery location and lineage. Procurement may choose suppliers and split quantities but may not redefine those Planning facts.

## 5. Allocation Family contract

### 5.1 Identity

The authoritative family key is:

```text
service_date
+ delivery_location_id
+ ingredient_id
+ unit_id
```

For school operations this is the governed Atlas equivalent of v1's date + school + ingredient family. Different units always remain separate families.

### 5.2 Demand and lineage

```text
family_demand = Σ current released Purchase Handoff contributions
```

The backend owns aggregation. React never reconstructs family totals from raw rows.

Every family revision stores exact contribution references to the Purchase Handoff line revisions that produced the total. Superseded source revisions do not contribute to the current family read.

### 5.3 Persisted objects

Add exactly these school-catering Procurement tables under `atlas_procurement`:

- `school_catering_allocation_families`
- `school_catering_allocation_family_revisions`
- `school_catering_allocation_family_contributions`
- `school_catering_allocation_supplier_splits`

Do not add a generic allocation engine, workflow engine, queue, event-sourcing layer, or JSON-polymorphic authority.

`school_catering_allocation_families` is the stable family root.

`school_catering_allocation_family_revisions` is immutable revision history and stores at minimum:

- family ID;
- revision number;
- source Purchase Handoff fingerprint/currentness reference;
- authoritative family quantity/unit;
- accepted actor/time;
- predecessor revision;
- command ID.

`school_catering_allocation_family_contributions` maps one family revision to every exact Purchase Handoff line revision contributing quantity.

`school_catering_allocation_supplier_splits` stores immutable accepted supplier splits for one family revision, including supplier, allocated quantity and server-calculated split ratio.

A new accepted allocation creates a successor family revision; prior revisions remain historical.

### 5.4 Read-state vocabulary

The backend read model derives operator state rather than asking React to interpret raw revisions:

- `UNALLOCATED` — no accepted current allocation;
- `BALANCED` — accepted current allocation exactly matches current family demand and eligibility;
- `STALE_REBALANCE_AVAILABLE` — source demand changed and prior eligible ratios can produce a proposal;
- `NEEDS_REALLOCATION` — source changed but prior supplier set can no longer be safely carried forward;
- `BLOCKED` — source/eligibility/invariant failure prevents allocation.

Vietnamese UI labels must be friendly and must not expose raw backend status codes as primary copy.

## 6. Supplier recommendation and confirmation

For an untouched family the backend recommendation is:

```text
eligible supplier with the lowest numeric priority value = 100% of family demand
```

Priority ranks suppliers; it is not a capacity ratio. Atlas must never infer 60/40 or other automatic split percentages from priority.

If no eligible supplier exists, or more than one supplier shares the best priority, the family is an exception and no authoritative allocation is created.

Recommendations become authoritative only through explicit operator action:

- `Lưu phân bổ` for one edited family;
- `Xác nhận phân bổ đề xuất` for eligible untouched proposals.

Bulk confirmation payloads must contain the explicit family IDs plus expected source/revision fingerprints returned by the current read. The server re-reads every candidate and skips stale/ambiguous/edited/ineligible families rather than confirming an unseen broad scope.

## 7. Exact supplier split invariant

For every accepted family revision:

- one or more supplier splits;
- supplier unique within the revision;
- every split quantity > 0;
- supplier active;
- supplier eligible for the ingredient on the service date;
- split unit equals family unit;
- `Σ allocated_quantity = family_demand` exactly.

The server calculates `split_ratio`; client-authored ratios are ignored/rejected as authority.

## 8. Rebalancing

If demand changes from 100 kg to 120 kg and the current accepted split was 60% / 40%, the backend may propose 72 kg / 48 kg only if the same suppliers remain eligible.

The proposal is non-authoritative until operator confirmation.

### 8.1 Rounding

Apply the governed quantity precision. Calculate all but the final split from preserved ratios, then assign the exact residual to the final split so the proposal closes exactly to family demand.

### 8.2 Eligibility change

If any prior supplier becomes ineligible, do not silently redistribute its share. Return `NEEDS_REALLOCATION` and require operator action.

### 8.3 Draft impact

Only supplier/date drafts that depend on a changed allocation become stale. Unrelated suppliers, dates and schools remain current.

## 9. Shared Purchase Order aggregate

Reuse:

- `atlas_procurement.purchase_orders`
- `purchase_order_revisions`
- `purchase_order_lines`
- `purchase_order_line_revisions`

Do not create a separate school-catering PO subsystem.

### 9.1 Required narrow schema extension

Add `purchase_order_kind` to `purchase_orders` with at least:

- `SUPPLIER_DIRECT_WHOLESALE`
- `SCHOOL_CATERING`

Existing PA-05E inserts must remain compatible, using a migration-safe default/backfill of `SUPPLIER_DIRECT_WHOLESALE` where necessary.

For `purchase_order_lines`:

- make `fulfilment_allocation_line_id` nullable;
- add nullable `school_catering_allocation_family_id`;
- enforce XOR: exactly one source is non-null.

For `purchase_order_line_revisions`:

- make `fulfilment_allocation_line_revision_id` nullable;
- add nullable `school_catering_allocation_supplier_split_id`;
- enforce XOR: exactly one source is non-null.

For `purchase_order_revisions`:

- allow header `delivery_location_id` to be null for `SCHOOL_CATERING` multi-destination POs;
- preserve PA-05E wholesale behavior requiring one authoritative header destination through command/constraint validation;
- every PO line revision continues to carry its non-null delivery location and service date.

School-catering PO identity is:

```text
supplier_id + service_date + current non-cancelled school-catering PO lineage
```

One school-catering PO may contain many school/delivery-location lines for that supplier/date.

## 10. PO draft lifecycle

### 10.1 Create drafts

`Tạo đơn mua` uses `create_school_catering_purchase_order_drafts` for the selected service-date range/week.

Only current `BALANCED` family revisions participate.

The backend groups accepted supplier splits by supplier + service date and materializes PO DRAFT revisions with school/delivery-location lines.

PO draft quantity/supplier data is read-only. The PO screen is not a second allocation editor.

### 10.2 Blocked dates

If a service date contains any family that is unallocated, imbalanced, stale or blocked, that date is returned as not ready and no incomplete supplier PO is produced for that date.

Ready dates in the submitted range may be materialized in the same command; all actual writes performed by one invocation remain transactionally atomic. The response explicitly lists created/updated dates and skipped dates with blockers.

### 10.3 Regenerate stale drafts

A draft is stale when any source family/split revision is no longer current.

`Tạo lại đơn cần cập nhật` reuses `create_school_catering_purchase_order_drafts` and creates successor draft revisions only for affected supplier/date POs. Prior draft revisions remain historical.

### 10.4 Released PO immutability

A released PO is never regenerated by this slice. Later amendment/cancellation/replacement requires a separate approved Procurement contract.

## 11. PO release and automated numbering

`release_school_catering_purchase_order` releases exactly one current PO draft.

The command revalidates:

- expected PO version/current draft revision;
- all source family/split revisions current;
- supplier active;
- source eligibility still valid;
- exact supplier/date grouping;
- no release blocker;
- PO not already released.

On success the backend:

- allocates the official PO number server-side;
- records immutable release snapshot data;
- changes status to `RELEASED_TO_SUPPLIER`;
- records actor/time;
- emits one domain event and one audit event;
- returns authoritative readback.

The request must not accept `document_number`.

A draft has only internal UUID/reference. Official numbering occurs only at release.

Gapless numbering is not an MVP requirement. Number generation must be concurrency-safe and immutable once issued.

Bulk `Phát hành tất cả đơn sẵn sàng` is application convenience over independent per-PO release calls. Failure of one PO does not roll back other suppliers' successful releases.

For this slice, release records the official Atlas supplier commitment. PDF/export is the initial delivery mechanism and is not part of transactional command success.

## 12. Public API contract

Lock these five new command names:

1. Planning: `release_school_catering_purchase_handoff(request jsonb)`
2. Procurement: `save_school_catering_supplier_allocation(request jsonb)`
3. Procurement: `confirm_school_catering_supplier_recommendations(request jsonb)`
4. Procurement: `create_school_catering_purchase_order_drafts(request jsonb)`
5. Procurement: `release_school_catering_purchase_order(request jsonb)`

Lock these two read names:

1. `get_school_catering_procurement_workbench(request jsonb)`
2. `get_school_catering_purchase_orders(request jsonb)`

All use established Atlas safe command/read patterns rather than a new framework.

## 13. Read-model responsibilities

### 13.1 `get_school_catering_procurement_workbench`

Returns shaped data for `Phân bổ nhà cung ứng`:

- date/week and school scope;
- family identity and authoritative total;
- school/delivery-location, ingredient and unit display facts;
- contribution lineage summary;
- current accepted splits and ratios;
- eligible supplier choices with priority;
- 100% priority-1 recommendation when unambiguous;
- allocation/read state;
- stale/rebalance proposal;
- blockers/warnings;
- allowed actions and disabled reasons.

React does not aggregate handoff lines or decide eligibility/currentness.

### 13.2 `get_school_catering_purchase_orders`

Returns shaped data for `Đơn mua`:

- supplier/date PO list;
- draft/released status;
- current revision/version;
- school/destination line detail;
- source allocation revision references;
- derived draft staleness;
- release eligibility;
- official number when released;
- export readiness;
- blockers/warnings;
- allowed actions and disabled reasons.

## 14. Connected UI

The dormant Procurement prototype must not be polished into production unchanged.

Procurement should be a disciplined evolution of the current Planning workbench plus the master-data pages' dense table pattern, while intentionally avoiding their visual weaknesses.

### 14.1 Shared operating context

Use a lighter context strip than Planning's current operating rail. Show only:

- delivery date range/week;
- school/delivery-location scope;
- search;
- exception filters;
- refresh/currentness.

Do **not** combine backend versions, command codes, both stage labels and primary actions into this same strip.

Use two clear stage tabs/segments only:

- `Phân bổ nhà cung ứng`
- `Đơn mua`

### 14.2 `Phân bổ nhà cung ứng`

Primary surface: dense Allocation Family table. One visible row means one **Allocation Family**, not one raw Purchase Handoff line.

Columns:

- Ngày giao
- Trường / điểm giao
- Nguyên liệu
- Nhu cầu
- Đã phân bổ
- Còn lại / chênh lệch
- NCC
- Trạng thái

Filters:

- week/date range;
- multi-school;
- search across school, destination, ingredient and supplier;
- Chưa phân bổ;
- Chưa đủ / lệch;
- Đã đủ;
- Cần phân bổ lại;
- NCC không phù hợp when applicable.

Selecting a row opens an attached contextual split panel rather than adding multiple row action buttons or navigating away.

The selected panel shows:

- family total and unit;
- eligible suppliers ordered by priority;
- current/previous split ratios;
- editable split quantities;
- exact allocated/remaining total;
- eligibility explanation;
- source trace only behind disclosure.

Primary actions are contextual:

- `Lưu phân bổ` for one edited family;
- `Xác nhận phân bổ đề xuất` for explicitly selected untouched recommendations;
- `Tạo đơn mua` when selected dates are ready.

There is no visible `Validate allocation`, `Approve allocation`, or other backend-state ceremony.

### 14.3 `Đơn mua`

Primary surface: supplier/date PO list and selected PO detail.

Example:

```text
02/09
  NCC A · 18 dòng · Bản nháp
  NCC B · 12 dòng · Bản nháp
  NCC C · 21 dòng · Đã phát hành
```

Selected PO shows:

- supplier;
- service date;
- school/destination lines;
- ingredient quantities/units;
- draft currentness;
- blockers/warnings;
- official number when released;
- export action.

Primary actions:

- `Tạo lại đơn cần cập nhật` for stale drafts;
- `Phát hành cho NCC` for one current draft;
- optional multi-select / `Phát hành tất cả đơn sẵn sàng` convenience;
- PDF/export after release.

There is no separate `Xuất đơn cho nhà cung ứng` lifecycle tab; export belongs to the PO surface.

### 14.4 Visual quality rules

Target Procurement above the current Atlas visual baseline:

- visual quality target: at least 7/10;
- interaction/product logic target: at least 8/10;
- architecture/contract target: at least 9/10.

Use:

- practical table text around 14px where density allows;
- ingredient and supplier names visually stronger than IDs;
- fewer bordered/beige panels than Planning;
- row selection plus contextual detail panel instead of many row buttons;
- one dominant action at a time;
- technical trace/audit behind progressive disclosure;
- natural Vietnamese operator vocabulary;
- responsive layouts that do not clip status text or create large empty containers.

Avoid:

- summary-card walls;
- large disabled forms;
- nested tab systems;
- competing top actions;
- technical identifiers in the primary scan path;
- large empty right-hand areas pretending to be content;
- the old prototype's seven equal-weight lifecycle buttons.

### 14.5 Persistent command outcomes

Important writes must leave a visible result state, not only a toast:

- what succeeded;
- affected families/POs/suppliers;
- resulting versions/currentness;
- official document number after release;
- blockers/warnings;
- retry/reload guidance;
- next allowed action.

## 15. Safe error/recovery classes

At minimum support:

- `SOURCE_CHANGED`
- `STALE_VERSION`
- `ALLOCATION_IMBALANCED`
- `SUPPLIER_INELIGIBLE`
- `NO_ELIGIBLE_SUPPLIER`
- `AMBIGUOUS_SUPPLIER_PRIORITY`
- `PO_DRAFT_STALE`
- `PO_ALREADY_RELEASED`
- capability/scope denied
- idempotent replay success
- retryable concurrency/transport failure
- unknown write outcome requiring authoritative reload.

SQL, role, RLS, JWT and stack details never reach the client.

## 16. Authorization and transaction safety

Reuse established Atlas patterns:

- authenticated subject resolution;
- active actor;
- capability check;
- relational school/delivery-location scope or GLOBAL;
- exact payload allowlists;
- idempotency/replay/conflict handling;
- expected-version concurrency;
- deterministic locks;
- command receipts;
- domain/audit events;
- least-privilege Planning/Procurement runtime roles;
- no direct authenticated private-table writes.

Do not broaden PA-05E runtime privileges merely to support school catering if a dedicated narrow runtime boundary is safer.

## 17. Automated-code policy outside this slice

Atlas operators should not type system-generated business identifiers.

UUID remains internal identity; human-readable codes are backend-generated business references.

This slice enforces that policy for PO numbers.

Current Admin `create_ingredient` and `create_supplier` APIs still require manual `ingredient_code` / `supplier_code`. That is explicit Admin contract debt and should be corrected in a separate bounded task after Procurement planning; do not expand this Procurement migration with unrelated master-data changes.

Do not create one giant cross-domain numbering service. Each owning domain should own its numbering namespace with only narrowly shared concurrency/format helpers where useful.

- exact school-catering Purchase Handoff materialization;
- deterministic family grouping and complete contribution lineage;
- recommendation remains advisory until explicit confirmation;
- family save atomicity;
- exact split balance;
- duplicate/ineligible suppliers fail closed;

### 18.2 Frontend

Prove:

- routed screen uses connected reads/commands, not fixtures;
- family table is primary;
- date/school filters do not become write authority;
- recommendations require explicit confirmation;
- family edits submit complete split set;
- imbalance prevents save/draft creation;
- stale/rebalance behavior is visible and recoverable;
- stale PO cannot release;

- persistent command outcomes/recovery are rendered;

### 18.3 Cross-stage rehearsal

Certify the real flow:

```text
Menu / Attendance / Pantry

→ Confirmed Need

→ Purchase Handoff
```

## 20. Implementation decomposition

The implementation plan should keep one architectural workstream but execute in bounded reviewable slices:

1. School-catering Purchase Handoff backend boundary and Planning integration.
2. Allocation Family persistence, aggregation and read model.
3. Manual family save + bulk default confirmation + rebalance behavior.
4. Shared PO aggregate extension and supplier/date multi-school draft generation.
5. Per-PO release, automated official numbering and immutable release snapshot.
6. Connected two-stage Procurement UI using shaped reads/commands.
7. Cross-stage integration + hosted browser certification.

Each slice must use the same exact vocabulary and contract. Do not re-open architecture inside each task.

## 22. Acceptance definition

The first connected school-catering Procurement capability is complete when an authorized operator can:

1. release confirmed school-catering demand through a durable Purchase Handoff;
2. see backend-generated Allocation Families at the correct date/location/ingredient/unit grain;
3. accept the priority-1 default or split one family across multiple eligible suppliers;
4. preserve/reuse split ratios for safe rebalance after upstream demand changes;
5. bring relevant families to exact balanced allocation;
6. create PO drafts for selected ready service dates;
7. inspect supplier/date multi-school PO drafts;
8. release each current PO independently;
9. receive a backend-generated official PO number;
10. export the released PO;
11. retain exact traceability from PO line → supplier split/family → Purchase Handoff → Confirmed Need;
12. prove upstream edits propagate to unreleased Procurement work without silently rewriting released supplier commitments.
