# PA-02 — Physical Schema and Constraint Design

**Status:** Proposed architecture design; documentation only

**Scope:** PostgreSQL/Supabase physical design for the approved Atlas MVP

**Authority:** AGENTS.md, ARCH-001, ARCH-002, PA-01, approved domain contracts and decisions, current in-memory prototypes, and operator reviews

**Companion decision:** `docs/decisions/decision-pa-02-physical-schema-boundaries.md`
**Next gate:** PA-03 authorization, RLS, and command-surface design after PA-02 approval

## 1. Executive summary

PA-02 translates the logical persistence contract in PA-01 into a proposed physical PostgreSQL design without creating a database object. Atlas should use private, domain-owned schemas; lowercase `snake_case` names; opaque database-generated UUID primary keys; typed foreign keys and bridge tables for the operational lineage spine; exact decimal quantities; explicit immutable revisions and release snapshots; append-only stock and evidence records; and derived views/RPC results for workbenches.

The principal decisions are:

- use `atlas_core`, `atlas_admin`, `atlas_planning`, `atlas_procurement`, `atlas_evidence`, `atlas_warehouse`, `atlas_dispatch`, `atlas_audit`, `atlas_reporting`, and `atlas_legacy` as the namespace direction;
- keep all domain tables private by default and expose only reviewed views/RPCs later;
- use PostgreSQL `uuid` primary keys generated in the database with `gen_random_uuid()` for the first migration baseline; do not encode time, document numbers, or business meaning in IDs;
- use domain-local `text` columns with named `check` constraints for most statuses, reference tables for operator-managed vocabularies, and PostgreSQL enums only for exceptionally stable infrastructure vocabulary;
- store operational quantities as `numeric(20,6)`, conversion factors as `numeric(24,12)`, and never use binary floating point;
- store instants as `timestamptz`, store the Asia/Bangkok operating date separately as `service_date date`, and snapshot the applicable service window and timezone when released;
- model released document families with stable roots, immutable revisions, stable line identities, immutable line revisions, and release snapshots where the downstream commitment must remain interpretable;
- make `evidence_applications` a mandatory physical concept linking a valid evidence quantity to one exact fulfilment-allocation-line revision;
- keep live safety gates—stock availability, evidence sufficiency, departure readiness, reconciliation, and unresolved exceptions—in transactional command logic over authoritative tables, not in React or asynchronous materialized views;
- start the connected implementation with one supplier-direct wholesale line; add the warehouse-stock path as the next bounded slice.

Still requiring review before the first migration are the final namespace approval, document-number formats, unit-specific rounding policy, service-date cutoff policy, evidence-file storage contract, idempotency retention, exact lock/isolation policy, RLS surface, legacy inventory, and the exact first-slice acceptance fixture. The UUID recommendation is intentionally conservative: Supabase currently documents `gen_random_uuid()` and the target platform baseline is PostgreSQL 17, while native `uuidv7()` is a PostgreSQL 18 feature. Atlas may reconsider UUIDv7 under a later ADR after the target runtime provides a supported, tested generator; ordering must never be inferred from the ID.

No migration is added because names, constraints, access surfaces, and command gates require architecture/product review before they become expensive-to-reverse database history.

## 3. Global column conventions

### 3.1 Naming and identity

| Concern           | Physical convention                                                                                                                                                                                                         |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Identifiers       | Lowercase `snake_case`; table names plural; primary key named `<singular>_id`; constraints and indexes explicitly named. Avoid quoted identifiers.                                                                          |
| Primary keys      | `uuid not null primary key default gen_random_uuid()`. UUIDv4 is the PA-03 migration recommendation because it is supported on the current Supabase/PostgreSQL baseline without a new extension.                            |
| Foreign keys      | Same `uuid` type as target. Use typed FKs whenever a target is known. Index every operational FK used for joins or parent enforcement. Default `on delete restrict`; do not cascade-delete operational history.             |
| Canonical IDs     | Opaque, immutable, never reused, never derived from date/name/trace/document number. Chronology comes from timestamps, not UUID order.                                                                                      |
| Human references  | Separate `text` columns such as `document_number`, `trace_code`, `external_reference`; unique only in an explicit scope, normally `(series_id, document_number)` or `(source_system_id, source_object_type, source_key)`.   |
| Legacy references | Stored in `atlas_legacy.source_references`, never in primary keys and never sufficient alone for an authoritative cross-domain FK.                                                                                          |
| Versions          | Mutable aggregate roots carry `version bigint not null default 1 check (version > 0)`. Commands compare an expected version and increment once. Immutable revisions carry `revision_number integer` unique within the root. |

### 3.2 Time, actor, and command context

| Concern                      | Physical convention                                                                                                                                                                                                                                                                    |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `created_at`, `updated_at`   | `timestamptz not null`; `created_at` immutable, `updated_at` changes only with the root version. Immutable rows normally omit `updated_at`.                                                                                                                                            |
| `occurred_at`, `recorded_at` | Both `timestamptz not null` on evidence/events. `occurred_at` is the business observation; `recorded_at` is database acceptance. Require `recorded_at >= occurred_at` only where offline/future-clock policy makes that safe; otherwise validate skew transactionally.                 |
| `service_date`               | `date not null`, interpreted as the Asia/Bangkok operating date. Never derive it permanently by truncating a UTC timestamp.                                                                                                                                                            |
| Service windows              | `window_start_local time`, `window_end_local time`, `timezone_name text` (initially `Asia/Bangkok`) or immutable released window text/snapshot where execution depends on it.                                                                                                          |
| Actor                        | Prefer `actor_user_id uuid null references auth.users(id)` for a human; also store constrained `actor_type` and `actor_reference` for integration/delegated actors. Require a usable actor reference, preserve deactivated users, and never authorize from user-editable JWT metadata. |
| Command context              | `command_id uuid`, `correlation_id uuid`, and scoped `idempotency_key text`. Sensitive writes require a command receipt and carry `command_id` into events/evidence.                                                                                                                   |

### 3.3 Lifecycle, reason, and temporal columns

| Concern           | Physical convention                                                                                                                                                                                                                                                            |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Status            | Domain-specific `<object>_status text` with a named check constraint unless section 4 selects a reference table. No shared generic status column/table.                                                                                                                        |
| Reasons           | Use constrained `reason_code text` plus optional `reason_note text`. High-risk correction/cancellation/override requires at least one and may require both by command policy.                                                                                                  |
| Effective periods | `effective_from date not null`, `effective_to date null`; half-open interval `[effective_from, effective_to)`, check `effective_to > effective_from`. Overlap exclusion is required per governed scope when concurrent rules are not allowed.                                  |
| Active/inactive   | Reference data uses a domain status and optional effective period. Operational records use lifecycle/cancel/void facts instead.                                                                                                                                                |
| Archive           | `archived_at timestamptz null`, `archived_by_user_id uuid null`, after retention allows. Archive changes default visibility only; it never breaks traceability.                                                                                                                |
| Supersession/void | `superseded_by_<type>_id` or `voided_by_<type>_id`, plus actor/time/reason on the correcting record. Use typed links, not generic IDs.                                                                                                                                         |
| Metadata JSON     | `jsonb` only for bounded, non-authoritative extension metadata, canonical command response replay, or source payload checksum context. Required relationships, quantities, statuses, and safety fields stay typed. Add a GIN/expression index only for an approved query path. |

### 3.4 Quantity and numeric baseline

- Operational quantities: `numeric(20,6)` with explicit `unit_id` FK.
- Unit-conversion factors and intermediate calculation factors: `numeric(24,12)`.
- Portion counts: `integer` or `bigint` as appropriate, constrained non-negative.
- Sequence/revision/stop order/package count: integer/bigint, not numeric quantity.
- No `real`, `double precision`, JavaScript-derived binary float, or text quantity in authoritative storage.
- Zero is allowed only where the domain meaning is explicit: attendance zero, excluded/cancelled Planning line, or zero-result calculation. Evidence applications, posted stock movements, released PO/load/release/delivery quantities must be strictly positive.

## 4. Status and vocabulary strategy

| Option                       | Strength                                                                  | Cost/risk                                                                                   | Atlas use                                                                                                         |
| ---------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| PostgreSQL enum              | Compact and strongly typed.                                               | Value changes are schema changes; cross-domain reuse invites a generic workflow vocabulary. | Only exceptionally stable infrastructure vocabulary, if any, after PA-03. Not the default for business lifecycle. |
| `text` + named check         | Clear, local, easy to review and extend through migration.                | Each table needs an intentional constraint; renames still require migration.                | Default for aggregate/line/evidence lifecycle and fixed command-owned kinds.                                      |
| Lookup/reference table       | Effective-dating, labels, ordering, operator governance, and translation. | A join and governance lifecycle; unsafe if used to invent runtime states.                   | Units, reason codes, service/menu categories, configurable policies, and other managed reference data.            |
| Domain-specific status table | Can capture transition evidence or policy per domain.                     | Easily becomes a workflow engine or duplicates audit.                                       | Use only when a future domain contract requires configurable transitions; none in the first slice.                |

Recommendation: use domain-local `text` plus named checks for fixed lifecycle values such as PO, evidence, trip, and receipt statuses. Use reference tables for vocabularies staff must manage or effective-date. Never create one generic status table, transition table, or workflow engine. Event/audit rows explain transitions; they do not govern all domain lifecycles.

## 5. Table catalog

## 6. Cross-domain line identity design

The spine uses stable line IDs and exact immutable line-revision IDs. A stable line answers “which obligation?”; a line revision answers “which released facts were acted on?”

| Source → target                                        | Required physical link                                                                                | Polymorphism / bridge                                                                                                                                            | Snapshot and duplicate constraint                                                                                         |
| ------------------------------------------------------ | ----------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Planning source line → theoretical need line           | Direct typed Menu snapshot-line, Attendance snapshot-line, RecipeLine, and RecipeLineRevision FKs on the atomic line. | H0A5a uses bounded typed run-owned Recipe selection/use relations where evidence is shared; generic `source_type/source_id` and generic source registries are rejected. | Input snapshot freezes exact evaluation/source/calculation facts; one atomic anchor tuple per run.                        |
| Theoretical need line → confirmed need line            | Direct FK from `confirmed_need_lines` and exact FK from line revision/snapshot.                       | No polymorphism.                                                                                                                                                 | Unique non-additive theoretical line per batch; approved snapshot freezes quantity/unit/source.                           |
| Confirmed need line → purchase handoff line            | Direct stable-line FK plus exact confirmed line revision/snapshot FK on handoff line revision.        | No polymorphism.                                                                                                                                                 | Unique source line per handoff root unless revision kind is additive.                                                     |
| Handoff line → dispatch requirement line               | Direct stable handoff-line FK and exact handoff-line-revision FK.                                     | No generic source reference. A typed source bridge may be added only if a future approved Planning source bypasses handoff.                                      | Requirement line revision snapshots item, quantity, unit, destination, and trace; uniqueness blocks duplicate release.    |
| Dispatch requirement line → fulfilment allocation line | Stable line FK plus exact requirement-line-revision FK on allocation line revision.                   | No polymorphism.                                                                                                                                                 | Split portions have their own stable IDs; unique source/portion key within allocation revision; command reconciles total. |

| Load line → delivery outcome                           | Direct FK from confirmation line and exception/return to exact load line.                             | No polymorphism.                                                                                                                                                 | One load line per confirmation revision; exact reconciliation transactionally enforced.                                   |

Canonical source-to-outcome query path:

```text
planning input evaluation + exact Menu/Attendance snapshots
→ bounded typed Recipe selection/use evidence
→ theoretical_need_lines with direct typed atomic anchors
→ confirmed_need_lines + confirmed_need_line_revisions
→ purchase_handoff_lines + purchase_handoff_line_revisions
→ dispatch_requirement_lines + dispatch_requirement_line_revisions
```

`trace_code` and legacy IDs are searchable attributes only. They never replace this FK path.

Generic `source_type` / `source_id` pairs are acceptable only for non-authoritative audit/event correlation or raw legacy staging where the source cannot yet be typed. Every operational Planning, Procurement, evidence, Warehouse, and Dispatch relationship uses a declared typed foreign key or a typed bridge table with exactly-one-source checks.

## 7. Revision and immutable snapshot physical design

### 7.1 Common mechanics

- A document series/root owns the stable business identity and concurrency `version`.
- A revision owns immutable released facts and a `revision_number` unique in the series.
- A stable line survives revision. A line revision belongs to one document revision and points to its predecessor when changed.
- `BASE`, `SUPERSEDING`, `ADDITIVE`, `CANCELLATION`, `CORRECTION`, and `REVERSAL` are domain-constrained revision kinds, not a generic workflow.
- A partial unique index enforces one current superseding revision per root. Additive revisions are current contributions and do not mark the base superseded.
- Pre-release correction updates only a draft root/revision through expected-version commands and audit. Post-release correction creates a new immutable revision, additive line, cancellation, or compensation.
- Historical queries never filter away superseded/voided facts; current-work queries use the explicit current/valid predicate.

### 7.2 Document-family pattern

| Family                                  | Physical pattern                                                                                              | Required behavior                                                                                                       |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Planning release / Dispatch requirement | Root + document revision + stable lines + line revisions.                                                     | Base and late additive releases coexist; superseding revision is unique; destination/item/quantity snapshots immutable. |
| Purchase Handoff                        | Root + revision + stable lines + line revisions + purchase-demand snapshot.                                   | Released demand never changes; new Planning approval creates successor/additive handoff.                                |
| Fulfilment allocation                   | Root + revision + stable portion lines + line revisions.                                                      | Prior splits remain visible; evidence stays on the exact old revision; reallocation never moves evidence.               |
| Purchase Order                          | Root + revision + stable lines + line revisions + supplier confirmations.                                     | Released supplier commitment immutable; revise/cancel/replace explicitly.                                               |
| Goods Receipt                           | Released root/lines plus correction/reversal records and stock movements.                                     | Do not reopen a posted receipt in place; correction or reversal offsets physical/ledger effect.                         |
| Warehouse Stock Release                 | Root + revision + immutable release lines + handoff evidence + movement.                                      | Release evidence and negative stock movement are atomic or protected by an unobservable internal state transition.      |
| Dispatch Load                           | Root + immutable confirmed lines + evidence-application bridges; simpler versioned draft before confirmation. | Protected after departure; correction/void requires successor, never edits evidence links.                              |
| Delivery Confirmation                   | Root/evidence + immutable lines; superseding confirmation.                                                    | Exactly reconciles a stop/load outcome; prior confirmation remains visible.                                             |
| Delivery Exception / Return             | Append-only evidence roots with status, supersession/void links.                                              | Exception resolution is explicit; return never posts Warehouse stock.                                                   |

## 8. Evidence and evidence-application design

### 8.1 Evidence envelope

Each source evidence table contains its own ID/kind, source owner, exact observed item and upstream reference, `evidence_quantity numeric(20,6)`, `unit_id`, immutable item/unit snapshot, actor, `occurred_at`, `recorded_at`, external reference, command/correlation IDs, optional attachment link, and status `VALID`, `SUPERSEDED`, or `VOIDED`. A correction inserts a successor and links the original; void requires source-owner authority and reason.

### 8.2 Application invariants

`atlas_evidence.evidence_applications` contains:

```text
evidence_application_id
supplier_receiving_evidence_id | supplier_cross_dock_evidence_id |
  warehouse_stock_release_line_id
fulfilment_allocation_line_revision_id
applied_quantity
unit_id
normalized_quantity
normalization_unit_id
conversion_rule_id / conversion_rule_snapshot
status
supersedes_evidence_application_id
command_id / actor / occurred_at / recorded_at / reason
```

Constraints and enforcement split:

| Invariant                                                         | Plain constraint/index                                                                          | Transactional command logic                                                                                                                                                                                |
| ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Exactly one evidence source and one allocation-line revision      | Check constraint plus typed FKs.                                                                | Verify source owner/capability and that source path matches allocation source.                                                                                                                             |
| Positive applied quantity and valid unit                          | Check and unit FK.                                                                              | Resolve approved conversion effective at occurrence and snapshot it.                                                                                                                                       |
| Duplicate active application rejected                             | Partial unique index on each typed evidence FK + allocation-line revision where status `VALID`. | Idempotency returns the prior command result; conflicting payload fails.                                                                                                                                   |
| Sum of active applications does not exceed evidence quantity      | Not safely expressible as a row check.                                                          | Lock evidence row, sum valid applications in normalization unit, reject over-application, insert atomically.                                                                                               |
| Valid applied quantity counted only for exact allocation revision | FK makes revision exact.                                                                        | Reject wrong source/item/unit and any implicit use of old evidence for a new allocation revision.                                                                                                          |
| Reallocation does not move evidence                               | No update permission; immutable applications.                                                   | New source-owner command must explicitly create application to the new revision if factually valid.                                                                                                        |
| Evidence supersession/void                                        | Typed successor FK and status check.                                                            | Lock evidence and applications; mark prior non-current, insert successor/application changes, re-evaluate affected un-departed loads; reject unsafe post-departure silent change and open correction path. |
| Load does not double-consume applications                         | Unique load/application bridge and positive quantity checks.                                    | Lock application rows; sum load consumption; reject excess or evidence gaps.                                                                                                                               |

Departure never trusts a cached `evidence_ready` flag. The departure command locks/re-reads the trip, confirmed load lines, exact allocation-line revisions, valid evidence applications, and any evidence supersession/void state; it rejects unless every loaded portion remains sufficiently covered.

## 9. Quantity, unit, and rounding design

- Store all operational quantities in `numeric(20,6)`. This permits six fractional digits while retaining ample range for aggregate purchasing and stock.
- Store conversion factors/intermediate ratios in `numeric(24,12)`. Persist the rule ID, rule revision/effective date, input/output values, and rounding result used for every released calculation.
- Every quantity has a `unit_id`. A display unit is presentation only; authoritative storage uses the unit in which the fact occurred plus a normalized quantity when cross-unit reconciliation is required.
- Unit conversions are directed rules, scoped by ingredient/supplier when needed, effective-dated, non-overlapping, and never inferred by multiplying arbitrary paths without an approved resolver.
- Evidence stores the observed quantity/unit. Applications store applied quantity/unit plus the exact normalization rule snapshot. Dispatch loads and destination outcomes retain their own observed units and must reconcile through the same approved rule.
- Rounding occurs at the contract-approved business boundary—recipe calculation, purchase packaging, or document release—not on every read. The unrounded value, rounded value, rounding mode, increment/package rule, and rule version remain traceable.
- For H0A5a Need Generation, sum exact student and teacher portions, multiply by RecipeLineRevision quantity, divide by RecipeVersion basis, evaluate in unconstrained PostgreSQL `numeric`, and coerce once at the final line boundary to `numeric(20,6)` using PostgreSQL half-away-from-zero tie behavior. Recipe factors use `numeric(24,12)`. This scale coercion is calculation storage, not Planning or purchase-policy rounding; overflow, non-finite client arithmetic, or a required Unit conversion fails the run.
- Overage and shortage are explicit non-negative quantities with a reason/status; they are not encoded as an ambiguous signed received quantity. Stock movements are the exception: ledger `quantity_delta` is deliberately signed and non-zero.
- Zero is accepted for attendance and explicit excluded/cancelled Planning outputs. Released physical, commitment, evidence-application, load, movement, and delivery quantities are strictly positive.
- Binary floating point is prohibited in migrations, RPC calculations, generated types, and client payload validation for authoritative quantities.

## 10. Time and service-date design

- Use `timestamptz` for all instants and preserve `occurred_at` separately from `recorded_at` for offline/late evidence.
- Use `service_date date` as the local Asia/Bangkok operating date. Store `timezone_name = 'Asia/Bangkok'` on service calendar/released service-window snapshots so future regional expansion is explicit.
- A service window uses local start/end plus timezone; cross-midnight windows require an explicit `ends_next_day` or resolved start/end instants in the released snapshot.
- `document_date` is the issue/commitment business date; it must not substitute for `service_date`. `delivery_date` is a requested/committed delivery date and may differ from PO issue date.
- Late arrival attribution is not inferred from `recorded_at`. Source commands accept the observed occurrence and service-date context, validate allowed clock skew/cutoff, and record late status in a derived view or explicit evidence issue.
- The exact 02:00 operating-day cutoff and policy for events recorded after midnight/after service remain open. PA-03/command design must choose whether the caller supplies service date with validation or the backend resolves it from a service calendar.
- Audit/evidence requires actor, command, occurrence, recording, and release/confirmation timestamps. Planned and actual departure remain separate.

## 13. RLS and access-surface preview

PA-02 does not create grants, policies, roles, or functions.

- Never expose directly to React: command receipts, document-number counters, all mutable domain roots/children/revisions, evidence applications, stock movements/reservations, audit event tables, legacy mapping tables, and attachment storage locators.
- Read through views/RPC only: Planning/Procurement/Warehouse/Dispatch workbenches, evidence readiness, stock availability, audit timeline, attention queues, diagnostic integrity, and cross-domain trace.
- Possible direct read after PA-03 review: narrow active reference views for units, ingredients, suppliers, customers, schools, and delivery locations. Prefer views so inactive/sensitive fields are intentional.
- Every business write uses an RPC/command. Direct table insert/update/delete is not a supported client API.
- Integration actors receive only declared command execution and read grants; no broad schema write. React never receives `service_role` or other secret credentials.
- Management/read-only users receive cross-domain reporting/audit views subject to sensitive-data filtering; management override is a separate reasoned command, not table access.
- If a view is exposed, PA-03 must choose `security_invoker = true` where underlying RLS should apply, or keep it private and expose a tightly granted function. Views can otherwise execute with creator privileges.
- Data API grants and RLS are separate layers. Custom schemas stay unexposed until both explicit grants/exposure and tested RLS/command authorization are approved.

## 15. Legacy evidence and migration staging

Before mapping, inventory each OPS v1/Retool source with system/environment, owner, object/table/query/export name, schema/column description, extraction method, key semantics, row counts/date range, write owner, data-quality limitations, credential handling, and Retool-derived/UI-only fields.

Migration staging:

1. Create an immutable extraction batch with source checksum, counts, extraction instant/range, owner, and completeness statement.
2. Load source rows into controlled staging outside authoritative domain tables; never execute Retool UI logic as Atlas logic.
3. Normalize source keys into `legacy_mapping_rows`; find duplicates by normalized business candidates, cross-source references, and operator review—not only exact strings.
4. Assign Atlas canonical IDs only after mapping acceptance. Record the legacy tuple in `legacy_source_references`.
5. Import through domain-owned migration commands that enforce the same constraints, snapshots, audit, and idempotency as normal commands.
6. Reconcile counts, totals, duplicate groups, rejected rows, sampled source-to-Atlas trace, and rollback criteria.

Potential master-data migration: reviewed customers/schools/locations, ingredients/units, suppliers/eligibility, dishes/recipes/lines. Selected open operational records require explicit cutover need and owner approval. Incomplete historical operations may remain read-only in OPS v1/archive with Atlas references.

Never copy Retool component/temp state, JavaScript transformers, event handlers, cached/duplicate derived rows, UI action flags, credentials/service keys, obsolete triggers/helpers, or unverified calculated outputs. Only one system owns writes for a workflow at a time; no dual write is implied.

After PA-02 is approved, **PA-03 should be a documentation-only Authorization, RLS, and Command Surface Design**. It should map capabilities and actors to every read model and command; decide exposed schemas/grants, RLS predicates, security-invoker views, function execution privileges, integration/emergency access, audit visibility, and authorization tests. It should also finalize idempotency, locking, and error contracts required by those commands. PA-03 should not silently become the first migration.

Only after PA-03 approval should a separately authorized implementation task create the minimal foundation migration for identity, command receipts, audit, the approved supplier-direct slice subset, grants/RLS, and transactional commands. That task must use version-controlled migrations, database tests, rollback/rehearsal notes, and no production-data write or cutover.

## Scope and migration effect

PA-02 adds documentation only. It adds no Supabase migration, SQL file, table, view, function, trigger, RLS policy, RPC, Edge Function, generated database type, Supabase client, backend integration, credential, production-data operation, Retool change, React behavior, fixture behavior, domain command, runtime test, or modification to ARCH-001/ARCH-002.

There is no database migration or rollback effect. Documentation rollback is a normal Git revert.
