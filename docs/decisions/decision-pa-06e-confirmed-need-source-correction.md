# Decision PA-06E — Confirmed Need Source Correction

**Status:** Proposed decision set; only rows explicitly labeled approved direction are settled

**Contract:** [PA-06E Confirmed Need Review, Adjustment, Revision, and Source-Correction Contract](../architecture/pa-06e-confirmed-need-review-adjustment-revision-contract.md)

**Implementation boundary:** [TASK-PA-06E Confirmed Need Revision Contract](../implementation-tasks/TASK-PA-06E-confirmed-need-revision-contract.md)

## 1. Context

Atlas already has a Planning-owned `ConfirmedNeedBatch`, stable `ConfirmedNeedLine`, versioned `ConfirmedNeedLineRevision`, approval snapshots, and separate approval and release states. A line revision stores both `theoretical_quantity` and `confirmed_quantity`, binds its calculation/source lineage, identifies its predecessor, and is current or superseded. Released snapshots and downstream documents are immutable.

PA-06D identified a future Planning review point but did not approve a new Quantity Decision object. PA-06E resolves that architectural question: the existing Confirmed Need revision is the decision-bearing object. This decision does not modify `PA-05D.v1`; direct-wholesale remains exact pass-through, with theoretical, confirmed, approved, released, and handoff quantities equal.

The table below distinguishes directions already approved by the PA-06E brief or existing approved contracts from recommendations that still require product-owner or architecture approval. A proposed row is not an accepted project decision.

## 3. Accepted architectural directions

The following are settled for future design unless superseded through change control:

1. Use the existing Confirmed Need aggregate and revision model; add no Planning Quantity Confirmation or generic Quantity Decision aggregate.
2. Keep calculated/theoretical quantity distinct from Planning-confirmed quantity.
3. Bind each decision to exact source/calculation and effective-policy evidence.
4. Correct upstream sources in their owning domains and express the operational consequence as a new Confirmed Need line revision.
5. Preserve approved, released, handoff, PO, and Dispatch history; never silently recalculate issued facts.
6. Keep direct-wholesale `PA-05D.v1` pass-through unchanged.
7. Keep Procurement authority over purchasable quantity and allocation; Planning may show only a labeled advisory consequence.
8. Treat the proposed API registry delta as non-canonical until a separately approved implementation task changes the registry.

## 4. Explicit non-decisions

PA-06E does not approve:

- a SQL schema, migration, RPC, grant, RLS policy, event implementation, or generated type;
- a React, Storybook, Retool, or other UI implementation;
- a new status, business aggregate, cross-domain correction workflow, or editable Purchase Handoff;
- school-catering CMD-03 behavior or any change to direct-wholesale CMD-03;
- production Planning or purchase step values;
- partial release, auto-reconfirmation, source-change cascading, or downstream document rewriting;
- direct access from browser roles to private Planning tables;
- a live Supabase, OPS v1, production-data, package, credential, or deployment change.

## 5. Consequences

The later backend design can remain narrow: an authorized review read, a deterministic preview, and one preview-bound confirmation command for a synthetic line. Approval, release, CMD-03 integration, Procurement, downstream correction, direct-wholesale, and live operations remain outside that slice.

Product and architecture review must close the pending rows before their behavior can become authoritative. Approved rows may be referenced as requirements, but no proposed function or capability is part of the canonical API registry merely because it appears in PA-06E.

## 6. Security, migration, and rollback effect

This decision record changes documentation only. It creates no database object, callable surface, role, grant, RLS policy, application behavior, live-system state, or deployment.

Future implementation must use backend authorization, exact scope, private tables, hardened function boundaries, idempotency, optimistic concurrency, preview/commit fidelity, safe errors, receipts, events, audit, and authoritative readback. Documentation rollback is a normal Git revert; no database rollback applies.
