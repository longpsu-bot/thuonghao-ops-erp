# School54 prerequisite for weekday synchronization

The approved parity mandate includes this bounded dependency repair. School54
was present and active in the original source evidence, with configured weekday
portions; the earlier claim that it was unconfigured was incorrect. The failed
weekday preview stopped before writes because its target mapping was absent.

## Contract and scope

The protected manual **Atlas Staging School54 Prerequisite** workflow creates
only the OPS v1 School54 Customer, Delivery Location and School. Their exact
source identities are `school:54:customer`, `school:54:delivery-location`, and
`54`; their target codes use the established v1 prefixes. The existing typed
SchoolType mapping is a read-only dependency and must match source facts.

The runner extracts a fresh complete immutable OPS v1 master snapshot through
the established read-only endpoint and normalizer. The SQL adapter validates its
complete envelope, checksum, entity identities and read-only proof before
narrowing the three-root closure. Relevant source diagnostic blockers, missing
address/dependency facts, identity collisions, preexisting roots or mappings fail
closed. It never invents addresses, adopts an unrelated identity or merges
School54 into another School.

Source null general defaults use the existing approved normalization to zero.
The new School starts with an empty weekday object. Configured Monday-Friday
370-student/20-teacher values belong to the subsequent ordinary authenticated
weekday synchronization, rather than becoming general defaults. Source display
order is preserved without changing another School's order.

## Protected execution

Dispatch only from main using its exact full current SHA. A native-shell gate
runs immediately after checkout and before dependency installation or repository
execution, requiring main dispatch, full lowercase SHA, exact HEAD/current fetched
origin/main equality and a clean checkout. Credentials are scoped to verified
steps. The runner independently requires exact-head Frontend and executed Full
Integration certification, the fixed Staging project, protected environment
values, verified TLS transport, the complete exact 138-migration list and its
20261105090000 tip, and the existing active unlinked technical Migration Actor.

The actual protected user authenticates, verifies its identity and successfully
calls the authorized School read before any privileged SQL, even for Preview.
After successful Apply and known-success replay, the same session verifies the
School's shaped facts and unchanged previously visible Schools. Local-scope
logout runs in finally; a cleanup error does not replace the primary failure.

## Preview, review and apply

Default `apply=false` runs the call inside an explicit database READ ONLY
transaction and has no persistent business, mapping or receipt writes. Apply
uses an explicit transaction with locked target tables.
Review the bounded artifact's `plan_checksum`, source `content_checksum`, root
identities and School facts. Raw extraction remains in memory and is not uploaded.
Apply requires `apply=true`, exact Staging project confirmation and that separately
reviewed plan checksum; there is no skip-certification/authentication CLI flag.

The stable plan binds all normalized source business facts, the exact three
CREATE actions, full expected migration history, Actor and fingerprints of all
preexisting Atlas table rows, typed mappings and receipts. Technical extraction
snapshot ID, export time, extractor version and enclosing snapshot checksum are
excluded from the content identity, allowing separately dispatched Preview and
Apply to agree when actual facts have not changed. Source or protected target
drift requires a fresh reviewed preview.

Apply runs atomically through the existing private master import identity,
validation, collision, materialization and mapping helpers. Its complete allowed
delta is three roots, three typed mappings and one completed receipt. It preserves
every preexisting row and receipt, including archived source history and native
adjustments. A late write/readback failure rolls back the entire operation.

The runner requests identical receipt replay only after a known successful Apply.
An uncertain transport or failed result ends execution without retry. Inspect the
existing receipt before any recovery; use reviewed forward correction rather than
root/receipt deletion. This one-time prerequisite's replay must occur before later
authorized School changes, since changed created facts deliberately fail its
replay guard. Subsequent preview reports an existing valid receipt separately
instead of creating another import.
